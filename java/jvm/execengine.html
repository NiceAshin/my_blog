    # 执行引擎

    预计阅读时间：9 分钟

    执行引擎是 JVM 把字节码变成机器指令的组件。物理机的执行引擎直接建立在处理器、缓存、指令集和操作系统之上；虚拟机的执行引擎由软件实现，因此可以屏蔽硬件差异，执行同一份 .class 文件。 HotSpot 采用“解释器 + 即时编译器”的混合模式，在启动速度和长期运行性能之间取平衡。

    # 1. 为什么不是纯解释或纯编译

    纯解释执行启动快，但每条字节码都要查表、分发，长期运行性能差。纯编译执行需要先把所有方法编译成机器码，启动慢，而且很多只执行一次的代码根本不值得编译。

    HotSpot 的做法是：

    • 方法第一次执行时由解释器逐条解释；
    • 热点方法达到阈值后，由 JIT 编译为本地机器码；
    • 编译后的代码直接执行，后续调用不再解释；
    • 解释器同时承担“降级兜底”，编译失败或去优化时还能继续运行。

    这就是“混合模式”，也是 java -version 输出里 mixed mode 的含义。

    # 2. 解释器

    解释器逐条读取字节码，按操作码跳转到对应的汇编片段。它的优点是无需等待编译，适合启动阶段、低频代码和脚本式运行。

    解释执行的核心开销在指令分发：每条字节码都要取指、解码、跳转。为了减少开销，HotSpot 使用模板解释器，把常用字节码对应的机器指令模板提前生成好，执行时直接跳转，而不是每次动态生成。

    解释器也是 JIT 的“安全网”。JIT 编译可能因为 Code Cache 满、编译线程忙、激进优化失败而回退，解释器保证程序仍然可以继续跑。

    # 3. JIT 编译器

    HotSpot 内置两个 JIT 编译器：

    编译器 特点 适用阶段
    C1（Client Compiler） 编译快，优化较保守 启动、C1-only 分层
    C2（Server Compiler） 编译慢，优化激进 长期运行的热点代码

    分层编译（Tiered Compilation）把执行分为多个层级：

    • 第 0 层：解释执行；
    • 第 1–3 层：C1 编译，带不同级别的 profiling；
    • 第 4 层：C2 编译，基于收集到的类型、分支、调用频率做深度优化。

    JDK 8 之后分层编译默认开启。它让应用先快速获得 C1 代码，再在热点稳定后升级到 C2，兼顾启动与峰值性能。

    # 4. 热点探测

    HotSpot 主要使用基于计数器的热点探测：

    • 方法调用计数器：方法被调用的次数；
    • 回边计数器：循环体执行次数，用于触发栈上替换（OSR）。

    当计数超过阈值，方法进入编译队列。阈值不是固定值，分层编译下由运行时动态调整。可以用参数观察：

    java -XX:+PrintCompilation -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining Demo
    1

    -XX:+PrintCompilation 会输出方法编译时间、编译级别、是否发生去优化。输出中的 made not entrant 表示旧编译代码失效，常见于类加载、去优化或依赖假设被打破。

    # 5. 可运行的观察示例

    public class JitDemo {
    static int sum(int n) {
        int s = 0;
        for (int i = 0; i < n; i++) {
            s += i;
        }
        return s;
    }

    public static void main(String[] args) {
        long total = 0;
        for (int i = 0; i < 1_000_000; i++) {
            total += sum(100);
        }
        System.out.println(total);
    }
}

    # 6. 常见优化手段

    • 方法内联：把短小、热点的方法体直接嵌入调用方，消除调用开销，是后续优化的基础；
    • 逃逸分析：对象没有逃出方法/线程时，可能标量替换或栈上分配，减少 GC 压力；
    • 循环优化：循环展开、边界检查消除、向量化；
    • 去虚化：类型 profile 稳定时，把虚调用转为直接调用；
    • 常量折叠与死代码消除：编译期能确定的表达式直接计算结果。

    这些优化依赖运行时收集的假设。一旦假设被打破（例如新类加载导致接口出现新实现），JIT 会去优化，退回解释或较低层级代码。

    # 7. 常见坑

    • 用 -Xint 做性能测试，得出“JVM 很慢”的结论；这不是生产模式。
    • 微基准测试没有预热，测到的是解释执行和 C1 编译阶段。
    • Code Cache 设置过小，JIT 编译被拒绝，日志出现 CodeCache is full。
    • 大量动态生成类，导致去优化频繁，性能抖动。
    • 把 -XX:CompileThreshold 调得很低，启动时编译线程抢占 CPU，反而更慢。
    • 只看平均延迟，忽略 JIT 预热期的长尾。

    执行引擎的核心取舍是“启动快”与“跑得快”。HotSpot 用解释器保底、用分层编译逐步优化，再通过去优化保证正确性。理解这条链路，才能解释为什么同一个方法在压测前几分钟和稳定后表现完全不同。
