# YOLO 系列模型选型参考

YOLO 系列版本多、分支杂，单看论文里的 mAP 很容易选错。实际选型要同时回答四个问题：业务精度底线是什么、目标有多小、部署端算力多少、团队能维护哪套工具链。下面给出一套可执行的选型方法。

## 1. 先明确业务约束

- **检测目标种类**：类别越多，越需要强特征和充足样本；几十类以上时，小模型容易混淆。
- **目标尺度**：远距离小目标需要更高输入分辨率，单纯换大模型不一定有效。
- **性能约束**：实时视频通常要求单帧 20–50ms；离线批处理可以牺牲延迟换精度。
- **部署环境**：云端 GPU、边缘 Jetson、ARM CPU、浏览器，支持的算子与量化能力完全不同。
- **维护成本**：研究型分支可能缺少持续维护，Ultralytics 系工具链更完整。

建议先写一张验收表：最低 mAP、最低召回、单帧延迟、模型体积、目标硬件、允许的误检率。没有这张表，选型会变成“哪个新就用哪个”。

## 2. 版本对比

| 版本 | 核心特点 | 优势 | 风险/限制 | 适用场景 |
| --- | --- | --- | --- | --- |
| **YOLOv5** | Ultralytics 早期主线，工程资料多 | 稳定、部署案例多、易改 | 结构较旧，新特性少 | 维护老项目、快速交付 |
| **YOLOv8** | 检测/分割/姿态/分类统一 API | 生态成熟、导出链完整 | 不同任务需分别选权重 | 大多数新项目的主力 |
| **YOLOv10** | 端到端、NMS-free 设计 | 降低后处理延迟，推理链路简单 | 生态与部署工具不如 v8 广 | 极致低延迟、可接受新框架 |
| **YOLO11** | Ultralytics 后续主线，结构与训练策略改进 | 精度/速度平衡更好，API 兼容 | 版本较新，需验证部署链 | 新项目、希望跟进主线 |
| **RT-DETR** | Transformer 检测器，端到端 | 无 NMS、复杂场景表现稳 | 显存与算力需求更高 | 服务器端、精度优先 |

“YOLOv10”与“YOLO11”不是简单的版本递进关系，前者偏学术端到端方案，后者是 Ultralytics 的工程主线。选型时看维护方、导出支持和社区案例，比看版本号可靠。

## 3. 按场景给建议

### 边缘设备实时检测

优先 `yolov8n/s` 或同级别 YOLO11 n/s，输入 320–640，导出 ONNX 或 TensorRT INT8。先测端到端延迟，包括解码、预处理、推理、NMS，不要只测模型前向时间。

### 服务器高精度检测

优先 `yolov8m/l` 或 YOLO11 m/l，GPU 批量推理。若目标密集、遮挡严重，可以用 RT-DETR 做对比。精度不够时先补数据，再换大模型。

### 小目标、航拍、工业缺陷

不要只换模型。提高 `imgsz`、使用切片推理（SAHI）、增加高分辨率样本，往往比从 s 换到 x 更有效。切片推理会增加后处理复杂度，要评估重叠区域的框合并。

### 移动端/浏览器

优先 nano/small 模型，导出 TFLite、CoreML 或 ONNX，做 INT8 量化。量化后必须用真实样本复测，避免小目标召回大幅下降。

## 4. 可复现的对比方法

固定数据与评估脚本，对每个候选模型跑同一套流程：

```bash
for m in yolov8n.pt yolov8s.pt yolov8m.pt; do
  yolo detect val model=$m data=dataset/data.yaml imgsz=640 batch=16 device=0
done
```

记录四项指标：

1. 验证集 mAP50-95 与每类召回；
2. 单张端到端延迟（P50/P95），不是平均 FPS；
3. 模型体积与显存占用；
4. 失败样本类型（漏检、误检、框不准）。

延迟测试要固定 batch、输入尺寸、预热次数和线程数。用笔记本风扇状态不同的两次测试做对比，结论没有意义。

## 5. 常见坑

- 只看 COCO mAP。COCO 与业务数据的类别分布差异很大，排行榜第一不等于项目第一。
- 用同一批数据训练和验证，指标虚高；应按场景、时间或设备切分。
- 忽略预处理耗时，模型 10ms、预处理 30ms，端到端仍然不达标。
- 盲目上大模型，边缘设备降频后 FPS 腰斩。
- 选择无人维护的分支，遇到算子不支持或导出 bug 无法解决。
- 不做量化后评估，INT8 之后小目标全部丢失。
- 把 NMS 当作可忽略的后处理，密集场景下 NMS 可能占一半延迟。

选型的正确顺序是：先定验收指标，再用真实数据跑基准，最后看工具链和维护成本。模型版本会继续更新，这套方法不会过时。
